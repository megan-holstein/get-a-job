# Design

## What it is for

A person's professional history is elicited once, kept as facts, and compiled into as many targeted resumes and application answers as they need, by a coding agent, with every claim traceable to something they said. The alternative it replaces is the chat-window rewrite: paste a resume, get a rephrasing, lose the context when the window closes.

## Decisions

- **Interviews are the source of truth; resumes are derived.** A resume is a lossy, target-specific view. Keeping the facts separately means a new target never starts from an old resume's omissions, and a claim is elicited once. Alternative rejected: one evolving master resume as the only record, which is what most people have and why their resumes only ever shrink.
- **One folder per target.** `resumes/<target>/` holds the Markdown and the PDF for one job or job family, and `targets/<target>.md` holds what the job is and what happened. Versions are folders, not suffixes, so the status of each application sits beside the document that was sent. Alternative rejected: git history alone, which cannot show two targets side by side.
- **`resumes/base/` is the untargeted resume.** Every targeted resume is a reordering and rewrite of it, so the base carries the current best framing and the targets diverge from it rather than from each other.
- **`profile.md` holds decisions, not facts.** Facts belong to a role; framing decisions ("these roles stay separate", "never a founder listing") cut across all of them and are the thing a new session most often gets wrong. Writing them down the turn the user makes them, with their words, is cheaper than re-arguing them.
- **The interview is written, in rounds.** The agent appends a round of questions to the interview file, the user answers in their editor, the agent extracts facts and appends the next round. The file is the record, so nothing is transcribed later, and a round costs one read and one write instead of a conversation's worth of tokens. The user answers at their own pace, over days if they like. Alternatives rejected: a live chat interview, which costs tokens on every turn and produces a transcript that must then be cleaned into facts; a separate interviewer session, which worked but made the user carry files between two agents.
- **Interviewing and writing stay separate.** A round is written to serve the fact base, not one target, so the facts stay general enough for the next target.
- **Drafting is three passes by three agents.** The first writes long and complete. The second, which has not seen the interviews and so cannot add, decides the one point each bullet makes and writes it short, leaving facts out and listing them. The third, which has seen only the resume and the scorecard, reads as the hiring manager and returns what fails a seven-question check. Splitting the work matters because the agent that holds every fact writes a summary of them, and the agent that chose the words defends them. Alternatives rejected: one pass with a length target, which produced spacious prose that was neither complete nor dense; and a second pass told to keep every fact and cut only words, which produced bullets two users called accurate but written like an AI summarizing its context (three-line bullets carrying four facts, chains of mechanisms, strings of abstract nouns).
- **The bullet rules follow practitioner consensus, and the evidence under them is thin.** The one strong study is a field experiment on 480,948 jobseekers in which writing assistance that improved clarity raised hiring by 8 percent (Wiles, Munyikwa and Horton, NBER working paper 30886, 2023). Recruiter eye-tracking (TheLadders, 2012 and 2018) found seconds of attention per resume and poor results for long sentences, from a vendor with small samples. The shape of a bullet comes from Laszlo Bock's XYZ formula (2014) and university career offices (MIT, Yale, Harvard): verb, accomplishment, result. Engineering hiring writers (Gergely Orosz) add that impact outranks technology and that tools go last. No controlled study supports a particular bullet length or shows that numbers raise callbacks; those are convention. The harness treats the rules as the field's working practice, not as proven.
- **The user edits the Markdown before any PDF exists.** The draft is opened in their editor as text; they change it directly and say when to build. Their edits are read back as decisions and recorded in `profile.md`. Alternative rejected: reviewing the PDF and relaying changes in chat, which costs a round trip per sentence and loses the user's own wording.
- **Versions are files the script writes, one per day.** Every build copies the Markdown and the PDF to `versions/YYYY-MM-DD.md` and `.pdf` and logs a note, overwriting any earlier build of the same day. The history then holds the resume as it stood at the end of each day it changed, which is the resume the user applied with, and none of the working drafts of a review session. The rule needs no judgment from the agent about which build matters. Restoring copies a dated version over `resume.md`. Alternative rejected: a version per build, which filled the history with drafts that lived five minutes (26 versions from one session). Alternative rejected: git history, which most users of this harness do not have for their resumes because the data is gitignored.
- **The build measures line endings.** A bullet that wraps two words onto a new line wastes the line, and an agent cannot see where text wraps in a PDF. The script lays the page out in headless Chrome at the printable width, measures each bullet's last line, and lists those under half full, so the agent cuts or extends them. Alternative rejected: a character-count limit per bullet, which cannot be right for a proportional font and a type size the auto-fit chooses.
- **Markdown master, scripted PDF.** The script renders a single-column, Helvetica, no-table, ligature-free document and verifies that every long word survives text extraction, because strict applicant-tracking parsers drop ligatures and tables. It auto-fits to two pages by trying spacing presets from roomiest to tightest; below the tightest preset the fix is trimming content, not type size. Alternative rejected: a word-processor template, which drifts from the content and cannot be regenerated by an agent.
- **Application answers are written from the facts, not from the resume, and kept.** A form's question asks for what the resume's compression cut (the problem, the reasoning, the evidence of use), so the answer is drafted from **Facts** and then checked against the resume sent to that employer. Answers are stored per target in `answers/`, because forms repeat their questions and an answer the user approved is the best start for the next one. A thin part of an answer opens an interview round, and the draft is delivered without waiting for it, since an application has a deadline. Alternative rejected: answering from the resume in chat, which can only restate bullets and leaves nothing behind.
- **User data is gitignored.** The public repository is the method; the history is the user's. A user who wants versioning forks privately and deletes the ignore lines, the same pattern as [tropestorm](https://github.com/megan-holstein/tropestorm).
- **Standard vocabulary is a rule, not a preference.** Postings and interview scorecards use the profession's names for practices; a resume written in private coinages is invisible to keyword screens and reads junior to a senior colleague. The agent corrects the user's language as it works.

## Evidence

The positioning rules rest on one published study of one employer (`docs/positioning.md`). The harness itself has no measured results yet. The measure that matters is response rate per target, which each `targets/<target>.md` records under **Status**; a user who keeps that log can see which framings worked.
